# Уведомления в afkaf — разведка и план

Дата: 30.09.2026. Ветка `feat/notifications` (от `feat/park-checkin`, внутри уже есть `feat/auto-finish`), папка `afkaf-rn-notify`.
Статус: **план согласован 30.09.2026** (решения владельца — раздел 8). Код не написан, ничего не установлено, сборки не запускались. Старт — по команде «поехали».

Что проверено по коду, а что — по памяти и требует проверки на устройстве, помечено отдельно (раздел 7).

## 1. Коротко

- Три сценария из четырёх (а, б, в) — **локальные уведомления** (телефон показывает их сам, без сервера). Нужна одна нативная библиотека `expo-notifications` и одна новая сборка. Дальше всё — обычный JS.
- Четвёртый (г, «друг вышел гулять») — **серверный пуш**. Новая нативная сборка для него уже не понадобится (всё нужное приедет с `expo-notifications`), но это отдельная большая работа на стороне Supabase.
- Главный технический вопрос — «успеет ли JS обработать кнопку без открытия приложения» — решается в нашу пользу: **во время прогулки приложение и так не спит** (его держит запись трека), поэтому нажатие кнопки приходит в уже работающий JS.
- Главная поправка к сценарию (а): кнопка «Ещё гуляю» имеет смысл только **до** авто-завершения. После него запись трека остановлена, и из фона iOS её возобновить не даст.
- Dev client нужен один раз — сразу после первого (нативного) коммита. Собирать из `exp/mapbox`, влив туда `feat/notifications`. Пробное слияние показало **один конфликт — в `docs/MAPBOX-RECON.md`**, код сливается сам.

## 2. Сценарии

### Порядок

Ты предложил а → б → в → г. Предлагаю **б → а → в → г**:

- **б проще, чем а.** Чек-ин на площадке живёт в отдельном модуле без привязки к экрану (`src/lib/parkCheckin.ts`), и функция ручного чек-ина `checkInHere()` уже готова. Для (а) нужно доработать детектор и «дотянуться» до логики завершения, которая сейчас сидит внутри `WalkScreen`.
- **б — лучшая проверка самого рискованного места** (кнопка с экрана блокировки → запрос на сервер без открытия приложения). В DevPanel уже есть «Тест: порог 1 мин» для площадки — проверка занимает минуту.
- а и б по объёму близки; если (а) важнее для тестеров — можно поменять местами, техника от этого не страдает.

### б) «Ты на площадке? Отметься» — кнопка «Я здесь»

**Где событие.** `src/lib/parkCheckin.ts`:
- вход в зону площадки подтверждается в `feedParkFix()` → `syncZoneState()` (в состоянии появляются `parkId` и `insideSince`);
- выдержка проверяется в `tickParkCheckin()` — там же сейчас срабатывает авто-чек-ин через 5 минут (`PARK_DWELL_MS`);
- ручной чек-ин — `checkInHere(markerId)`, вызывает серверную функцию (RPC) `park_checkin` с `p_manual = true`.

**Что делать.**
- При подтверждённом входе в зону — **запланировать** уведомление на «вход + 3 минуты» (система покажет его сама, даже если JS в этот момент не получит ни одного GPS-фикса). При выходе из зоны / конце прогулки — отменить.
- Кнопка «Я здесь» → `checkInHere(parkId)`. Функция уже возвращает причину отказа (`not_inside`, `no_active_walk`, `nobody`, `error`) — при отказе показываем второе короткое уведомление «Не получилось, открой приложение».
- После успеха — заменить уведомление на «✓ Отметили» (иначе человек не узнает, что сработало: приложение ведь не открывалось).
- Не показывать: гостям, при «Кто видит меня = никто», если уже отмечен вручную, если приложение открыто на экране (там есть карточка площадки). Один раз на заход в зону.

**Важно для текста.** Ручной чек-ин = согласие быть видимым **по имени для всех**. Это должно быть написано в самом уведомлении, а не подразумеваться.

**Объём:** ~1 сессия. Только JS. Сервер и БД не трогаем.

### а) «Уже дома?» — «Завершить» / «Ещё гуляю»

**Где событие.** `src/lib/autoFinish.ts` + `src/screens/WalkScreen.tsx`:
- кандидат на завершение появляется в `feedHome()` (вошёл в домашнюю зону, `candidate`, время входа = T) либо в `setAnchor()` (правило «неподвижность», когда дом не задан);
- срабатывание — `check()` → `WalkScreen.handleAutoFinish()` (строка ~630): сохраняет снимок прогулки, останавливает запись трека;
- показ итогов — при возврате в приложение (`resumeAutoFinish`) или на следующем запуске (`useApp.finalizeAutoFinishedOnStart`).

**Поправка к сценарию.** Это два разных уведомления:

1. **«Уже дома?» — заранее**, пока прогулка ещё идёт (через 10 минут после входа в домашнюю зону; авто-завершение — через 20). С кнопками:
   - «Завершить» → завершить сейчас, итог обрезать по моменту входа T (тот же путь, что авто-завершение);
   - «Ещё гуляю» → сбросить кандидата и не спрашивать снова, пока человек не выйдет из зоны и не войдёт опять.
2. **«Прогулка завершена в 18:42»** — после авто-завершения. **Без кнопки «Ещё гуляю»**: запись трека уже остановлена, а возобновить её из фона iOS не позволит (у нас разрешение «при использовании», не «всегда»). Нажатие открывает приложение на итогах.

**Что делать.**
- В `autoFinish.ts`: отдать наружу «кандидата» (сейчас он виден только в диагностике) и добавить метод «отклонить дом» — по образцу уже существующего `rejectStill()`. ~20 строк.
- Уведомление №1 планировать заранее на «T + 10 мин», отменять при подтверждённом выходе из зоны.
- Кнопки должны вызывать код, который сейчас живёт внутри `WalkScreen`. Нужен маленький «мостик» на уровне модуля — ровно как `subscribeWalkLocations()` в `walkTracking.ts`: экран регистрирует обработчики, обработчик уведомлений их вызывает.
- Уведомление №2 — одна строка в `handleAutoFinish()`.
- Правило «неподвижность» (дом не задан): для первой версии только уведомление №2. Заранее спрашивать сложнее — точка отсчёта там переезжает.

**Объём:** ~1 сессия. Только JS.

### в) Опасность рядом — «Всё ещё тут» / «Уже убрали»

**Где событие. Его в коде нет.** Во время прогулки ничего не следит за расстоянием до меток. Есть только:
- список меток на `WalkScreen` (`markers` из `useMapMarkers`);
- голосование — внутри компонента `MarkerCallout.handleVote()` (запись в таблицу `marker_votes`);
- **заготовки настроек** на экране «Настройки»: «Опасные метки рядом», радиус 50/100/150 м, «Не уведомлять о…». Они сохраняются (`notif_hazards`, `notif_radius`, `notif_ignore_types`), но **ни на что не влияют**.

**Что делать.**
- Новый модуль-детектор (по образцу `zoneDwell.ts`): получает GPS-фиксы и список активных меток-опасностей, срабатывает раз на метку за прогулку, когда ты подошёл ближе радиуса из настроек. Исключить: свои метки, метки, по которым уже голосовал, типы из «Не уведомлять о…», метки внутри домашней зоны.
- Вынести запись голоса из `MarkerCallout` в общий модуль (чтобы и карточка, и уведомление писали одним кодом).
- Подключить заготовки настроек к детектору.
- Гость голосовать не может → гостю уведомление без кнопок.

**Объём:** ~1,5 сессии. Только JS. Сервер не трогаем (голос пишется тем же запросом, что сейчас).

### г) «Друг вышел гулять» — серверный пуш (только оценка)

Источник события — появление строки в `active_walks` (`WalkScreen.createActiveWalkRow`). Телефон друга об этом не знает, значит, нужен сервер.

**Из чего состоит:**
1. **Токены устройств** (адрес телефона для пуша): новая таблица в Supabase + политики доступа (RLS), запись токена при входе, удаление при выходе из аккаунта.
2. **Серверная функция** (Supabase Edge Function) + срабатывание на вставку в `active_walks`: найти принятых друзей, их токены, отправить.
3. **Доставка.** Проще всего через сервис пушей Expo (он сам ходит в APNs у Apple и FCM у Google; ключ APNs хранит EAS). Для Android — отдельно завести ключ FCM.
4. **Правила, которых сейчас на сервере нет:**
   - настройка «Друг начал прогулку» лежит только в телефоне (`notif_friend_walk`) — перенести на сервер;
   - язык получателя (he/ru/en) — хранить рядом с токеном;
   - не слать при «Кто видит меня = никто» (тут строки и так нет);
   - **защита от повторов:** строка `active_walks` удаляется и создаётся заново при входе/выходе из домашней зоны — без защиты друг получит несколько пушей за одну прогулку.
5. `privacy.html` — заметная правка (новый вид данных и новые получатели).

**Объём:** 3–5 сессий + правки БД через ручной стоп (SQL текстом → «выполнил» → снимок в `supabase/`). **Новая нативная сборка не нужна**, если `expo-notifications` уже в сборке 0.2.0.

## 3. Техника

### Версия

`expo-notifications ~0.32.17` — это версия, которую Expo SDK 54 сам считает правильной (проверено в установленном `expo@54.0.35`, файл `bundledNativeModules.json`). Ставить командой `npx expo install expo-notifications` — она подберёт эту версию сама.
`expo-task-manager` (нужен Android для кнопок в фоне) уже стоит.

### Когда спрашивать разрешение

Согласен: **при первом старте прогулки, отказ прогулку не блокирует.** Две поправки:

- Спрашивать **после** того, как запись трека стартовала, а не вместе с геолокацией. Сейчас на первой прогулке уже идут подряд запросы геолокации и движения — третий диалог в ту же секунду почти гарантирует «Не разрешать».
- Системный диалог iOS показывается один раз в жизни. Поэтому перед ним — своя короткая карточка «Зачем» (напомним завершить прогулку и предупредим об опасности). Отказ в своей карточке системный диалог не тратит.

На Android 13+ ветка `exp/android` **уже** спрашивает это разрешение при старте прогулки (`walkTracking.ts`, ради уведомления «Прогулка идёт»). При объединении — оставить один запрос.

### Кнопки в уведомлении (notification categories)

| | iOS | Android |
|---|---|---|
| Кнопки на экране блокировки | Да. Видны по долгому нажатию / свайпу по уведомлению | Да, если в настройках телефона не скрыто содержимое уведомлений на экране блокировки |
| Нажатие без разблокировки | Да (кнопка объявляется как «не требует разблокировки» и «не открывает приложение») | Да на большинстве телефонов; отдельные оболочки просят разблокировать |
| JS получает нажатие в фоне во время прогулки | Да — приложение не спит, его держит запись трека | Да — процесс держит служба «Прогулка идёт» |
| Как получает | Обычный слушатель нажатий, зарегистрированный при загрузке приложения (в `index.ts`, не в компоненте) | **Через фоновую задачу уведомлений** (так сделано в библиотеке с версии 0.30.6 — проверено по её журналу изменений). Задачу объявить в `index.ts` |
| Успеет ли вызвать `park_checkin` | Да. Запрос — доли секунды, приложение и так активно в фоне | Да, по той же причине |

**Оговорка.** Всё это верно, **пока идёт прогулка**. Вне прогулки приложение спит, и кнопка без открытия приложения ненадёжна. Поэтому: кнопки «в фоне» — только у уведомлений во время прогулки; уведомление «Прогулка завершена» — без таких кнопок, по нажатию открывает приложение.

Ещё три вещи:
- Сервер и так страхует чек-ин: `park_checkin` требует свежую строку `active_walks` (не старше 10 минут) и расстояние до 150 м. Нажал «Я здесь» давно после ухода — получишь отказ, а не ложную отметку.
- Тексты кнопок задаются при регистрации категорий → при смене языка в приложении категории надо зарегистрировать заново.
- Когда приложение открыто на экране — уведомление не показываем (есть карточки в интерфейсе).

### Android: канал и служба «Прогулка идёт»

- Уведомление службы (foreground service) на `exp/android` создаёт сам `expo-location`, в **своём** тихом канале. Оно постоянное и висит всю прогулку.
- Наши уведомления — в **отдельном** канале (например, «Подсказки на прогулке») с высокой важностью, чтобы всплывали со звуком. Два уведомления живут рядом и друг другу не мешают: одно тихое постоянное, другое — разовое.
- Канал нужно создать **до** запроса разрешения (на Android 13+ система не покажет диалог, пока у приложения нет ни одного канала).
- Нужна отдельная маленькая иконка для статус-бара (белая на прозрачном, 96×96) — иначе Android нарисует белый квадрат. Задаётся в настройке плагина, то есть это часть нативной сборки: положить сразу в первый коммит.
- Бета iOS-first: Android-часть пишем сразу кроссплатформенно, но проверяем, когда `feat/notifications` доедет до `exp/android`.

### privacy.html

Файл `web/privacy.html`, три языка (he / en / ru), дата «Действует с 12 сентября 2026».

**Для а–в (локальные):** данные никуда не уходят, новых получателей нет. Добавить по одному пункту в каждом языке:
- раздел 2 или 3: «Уведомления — напоминания во время прогулки (завершить прогулку, отметиться на площадке, опасность рядом). Создаются на самом устройстве, на сервер ничего не отправляется. Отключаются в настройках телефона»;
- обновить дату.
Пункт «Никакого отслеживания вне активной прогулки» остаётся верным.

**Для г (пуши):** правка существенная —
- раздел 2: «токен устройства для уведомлений»;
- раздел 5: новые получатели — Apple (APNs), Google (FCM), Expo (сервис пушей);
- раздел 3: друзья получают уведомление о начале твоей прогулки (с учётом «Кто видит меня»);
- проверить анкету конфиденциальности в App Store Connect.

## 4. Сборка: один dev client «afkaf dev»

### Главная мысль

Dev client — это **нативная оболочка**. JS она берёт из Metro на маке, причём из **любой** папки. Значит:
- нативная часть уведомлений фиксируется **первым же коммитом** (библиотека + плагин). Всё остальное — JS;
- собрать dev client нужно **один раз**, сразу после этого коммита;
- дальше работаем в `afkaf-rn-notify`, запускаем там Metro — «afkaf dev» подхватывает JS оттуда. Для Mapbox — Metro из `afkaf-rn-mapbox`, то же приложение.

### Откуда собирать

**Из `exp/mapbox` (папка `afkaf-rn-mapbox`), влив туда `feat/notifications`.** Там уже есть всё для локальной сборки: `app.config.js` с вариантом dev (`com.afkaf.app.dev`), `scripts/patch-ios-local-build.js`, готовая папка `ios/`, профиль EAS `development-mapbox` для Android.

Заодно `exp/mapbox` получит чек-ин и авто-завершение. Это полезно: следующие экраны Mapbox по плану доходят до `WalkScreen`, который `feat/park-checkin` сильно поменял, — чем раньше ветки встретятся, тем дешевле.

### Почему конфликтов почти не будет

Проверено пробным слиянием `feat/park-checkin` + `exp/mapbox` (в памяти, без изменений в папках):

| Файл | Что будет |
|---|---|
| `package.json` | Сольётся сам: Mapbox добавил свою строку, уведомления добавят свою, строки разные |
| `package-lock.json` | Может сцепиться. Не разбирать руками — после слияния `npm install` пересоздаст |
| `app.json` | Меняем **только** его (плагин `expo-notifications`, версия). `exp/mapbox` этот файл не трогал |
| `app.config.js` | Есть только на `exp/mapbox`. **Его не трогаем**: он берёт список плагинов из `app.json` и дописывает Mapbox — плагин уведомлений подхватится сам |
| `src/components/DevPanel.tsx` | Сливается автоматически |
| `docs/MAPBOX-RECON.md` | **Единственный конфликт** (файл добавлен в обеих ветках). Взять версию `exp/mapbox` — она новее (есть итог фазы 1), сверить глазами |

Правило на будущее: **настройки уведомлений — в `app.json`, настройки варианта dev — в `app.config.js`**. Пока так, эти два файла не пересекаются.

### Шаги сборки (выполняет владелец или я по явной команде)

В папке `afkaf-rn-mapbox`, после слияния:

1. `npm install`
2. `APP_VARIANT=dev npx expo prebuild --platform ios --no-install` — папка `ios/` создаётся заново
3. `APP_VARIANT=dev node scripts/patch-ios-local-build.js` — возвращает правки под Xcode 27 и пробел в пути
4. `pod install` в `ios/`
5. `APP_VARIANT=dev npx expo run:ios --device`

Скрипт `patch-ios-local-build.js` менять **не нужно**: у `expo-notifications` нет своих скриптов сборки, которые ломаются на пробеле, а поднятие минимальной версии iOS у подов в скрипте общее.

**Ожидаемая заминка.** Плагин `expo-notifications` добавляет приложению право на пуши (entitlement `aps-environment`). Для `com.afkaf.app.dev` профиль подписи должен включать Push Notifications. При автоматической подписи Xcode обычно добавляет это сам; если сборка упадёт на подписи — один раз открыть проект в Xcode → Signing & Capabilities.

Android: `eas build --profile development-mapbox --platform android` (облако), по отдельной команде.

### Защита от падения (обязательно)

Модуль уведомлений подключать **только через проверку наличия** нативной части — как `walkTracking.ts` делает с `ExpoTaskManager` и как `src/lib/mapbox.ts` делает с Mapbox. Иначе JS из `feat/notifications`, открытый в старом dev client или в сборке без библиотеки, упадёт на старте. Один файл `src/lib/notifications.ts`, остальной код импортирует только его.

## 5. runtimeVersion

### iOS: 0.1.0 → 0.2.0

Сейчас: `version 0.1.0`, политика `appVersion` — обновление по воздуху (OTA) получают только сборки с той же версией.

- **Что поднять:** `version` в `app.json` → `0.2.0`.
- **Когда:** в **первом коммите** `feat/notifications`, вместе с библиотекой. Тогда ни из этой ветки, ни из `exp/mapbox` после слияния случайный `eas update` не долетит до тестеров на 0.1.0 (у них нет нативной части уведомлений — был бы краш).
- **Как тестеры не теряют OTA:**
  1. Пока уведомления в работе, `main` остаётся на 0.1.0. Все JS-правки тестерам идут как сейчас.
  2. **`feat/park-checkin` влить в `main` и отправить по воздуху отдельно, до уведомлений** — чек-ин и авто-завершение чисто JS, тестеры получат их на текущей сборке.
  3. Перед слиянием `feat/notifications` в `main` — поставить метку (git tag) на последний коммит 0.1.0. Если тестерам на старой сборке понадобится срочная правка, её можно будет опубликовать с этой метки.
  4. Слияние → preview-сборка → чек-лист → production-сборка 0.2.0 → TestFlight.
  5. С этого момента OTA из `main` идёт только на 0.2.0. Тестеры на 0.1.0 перестают получать обновления, пока не обновятся в TestFlight (обычно автоматически).
- **Совет:** каждая нативная сборка = «окно» для всех нативных изменений. В 0.2.0 стоит положить всё нативное, что уже готово (кандидат из бэклога — `expo-secure-store`). Mapbox — только если к тому моменту решён; иначе он станет 0.3.0.

### Android: android-1 → android-2

Строка `android.runtimeVersion = "android-1"` есть **только на `exp/android`** (в `main` и здесь её нет), канал — отдельный `production-android`.

**На `android-1` есть внешние тестеры** — 3–4 человека через Google Play Internal testing, канал `production-android`. Для них действует то же правило, что для тестеров TestFlight: JS с уведомлениями не должен долететь до сборки без нативной части.

- **Что поднять:** `android-1` → `android-2`, руками (это не `version`).
- **Когда:** строго в том коммите, которым уведомления вливаются в `exp/android`. Ни одного коммита с кодом уведомлений на `android-1` быть не должно — иначе `eas update` из этой ветки доставит его тестерам в Play.
- **До подъёма:** Android-тестеры продолжают получать JS-правки по воздуху на `android-1`, как сейчас.
- **Перед подъёмом:** поставить метку (git tag) на последний коммит `android-1` в `exp/android`. Срочную правку для тех, кто ещё не обновился, можно будет опубликовать с этой метки.
- **После подъёма:**
  1. сборка профилем `production-android` (.aab) → загрузка в Play Internal testing;
  2. тестеры обновляются через Play (автообновление не мгновенное — написать им);
  3. с этого момента `eas update --channel production-android` из `exp/android` идёт только на `android-2`; кто остался на `android-1`, обновлений не получает, пока не обновит приложение.
- Проверка на S9 (dev- или preview-сборка) — до загрузки в Play, как и для iOS.
- Бета iOS-first остаётся в силе: уведомления едут на Android отдельным решением, после iOS 0.2.0.

## 11. Решения 04.10.2026

**1. Звук — исправлено (коммит `f1f2392`).** Причина беззвучных уведомлений: в `content` не было поля `sound`. Без него iOS доставляет уведомление молча. Теперь во всех уведомлениях (`src/lib/notifications.ts`): `sound: 'default'`, `interruptionLevel: 'active'`, Android `priority: HIGH`. Android: новый канал `afkaf-walk-v2` (importance HIGH, звук, вибрация), на него переведены все уведомления, включая тест из DevPanel. Старые каналы `afkaf-walk` / `afkaf-test` удаляются: настройки канала после создания не меняются, поэтому нужен новый id.

**2. Time-sensitive — ВХОДИТ в октябрьскую нативную сборку**, только для двух уведомлений: **№2 «Уже дома?»** и **№4 «Ты всё ещё гуляешь?»**. Остальные три (№1 площадка, №3 опасность, №5 метка) остаются `active`. Принцип: срочность только там, где пропуск уведомления реально вредит (незавершённая прогулка, разряд батареи).

При подготовке сборки:
- entitlement `com.apple.developer.usernotifications.time-sensitive` в `ios.entitlements` (`app.config.js`) — для обоих вариантов: `com.afkaf.app` и `com.afkaf.app.dev`;
- проверить, включает ли EAS capability «Time Sensitive Notifications» в Apple Developer автоматически, или Влад включает её руками;
- в JS: `interruptionLevel: 'timeSensitive'` только для №2 и №4;
- проверка на телефоне: уведомление проходит сквозь включённый «Фокус».

**3. Свой звук уведомлений — планируется (Влад делает сам).** Фирменный тембр «звон жетона на ошейнике» + короткие вариации по типам: мягче для площадки и дома, настойчивее (две ноты) для опасности. **НЕ собачий лай** — собаки рядом на него реагируют.

Требования:
- iOS: `.wav` / `.aiff` / `.caf`, не длиннее 30 с;
- Android: `.wav` / `.mp3`, задаётся в канале → потребуется **новый id канала**;
- имена файлов латиницей, без пробелов.

Входит в нативную сборку (файлы подключаются через config-плагин, по воздуху не доставить).

**4. Идея на потом: Live Activity для активной прогулки** — таймер, дистанция, кнопка «Завершить» на экране блокировки и в Dynamic Island. Сначала — read-only разведка совместимости с Expo SDK 54 и сборкой на Xcode 26.
